# 中版本测试材料

每次准备 `vX.Y.0`（`Y > 0`）时建立同名目录，提交四个文件：

| 文件 | 最少应写明 |
|---|---|
| `baseline.md` | 原始需求来源和哈希、测试工程的干净起点、CLI/daemon/connector/EDA 版本、通过阈值与禁止预制答案的边界 |
| `test-cases.md` | 完整建模、局部修改、失败回退、保存重载等用例的输入、步骤、预期和判据；用例 ID 供报告引用 |
| `test-report.md` | 每个用例的实际命令、项目/文档、保存重载后的回读、判定、失败与修复记录、独立 Agent 复核结论及证据路径 |
| `manifest.json` | 精确版本、最终结论、独立复核结论和前三个文件的 SHA256 |

默认 schema 1 的用例表必须覆盖 `M1/F1/F2/E1/L1/N1/R1/E2E`，报告用同样的 ID、每行第二列
`pass` 和第三列不少于 30 字符的回读/证据引用。`L2` 可在没有真实缺陷时记
`not-applicable`，并在第三列说明前提为何不成立。报告还需有 `## 现场回读`、
`## 独立复核` 两节。机器只核对结构、结论一致性与哈希；真实测试是否充分仍由
独立复核者根据原始证据判断。

`manifest.json` 格式：

```json
{
  "schemaVersion": 1,
  "version": "v1.6.0",
  "result": "pass",
  "independentReview": "pass",
  "sha256": {
    "test-report.md": "<64 个小写十六进制字符>",
    "baseline.md": "<64 个小写十六进制字符>",
    "test-cases.md": "<64 个小写十六进制字符>"
  }
}
```

只有现场用例和独立复核全部通过，才能把两个结论写成 `pass`。先完成材料、计算三份
Markdown 的 SHA256、审阅并提交，再运行 `make release-check VERSION=vX.Y.0` 和
`make release-build VERSION=vX.Y.0`。后者生成 `test-evidence.zip`，发布时自动附上；
手工修改报告后必须重新计算哈希并重新审阅。报告可引用仓库内其他证据，但发布包只包含
这四个经过审阅的文件，不打包原始私有日志、凭据或测试工程数据。

## 本次基础 CLI 发布范围（schema 2）

2026-09-25 用户明确“发布新版本，然后高级 CLI 下个版本再验证”。本次材料使用
schema 2：`acceptanceScope: "basic-cli"`、`deferredScope: "advanced-cli"`、
`deferredUntil: "next-release"`。其余版本、哈希、独立复核字段与 schema 1 一致。
`result: "pass"` 只代表声明范围内通过。

用例和报告必须准确包含 B00–B10 与 A00–A06：前者每项 `pass`，后者每项 `not-run`，
每行保留不少于 30 字符的回读证据或延期说明。缺少任何基础项、基础失败、将延期高级项
写成通过、未知范围、未复核或哈希不一致都会阻止源码检查和发布包 smoke。
基准注明个人空间、既有自定义规则配置及 dev 候选到正式包的源码对应，发布说明同步披露。
不得改写旧 schema 1 的未通过结果；下一版本高级验收仍按完整需求流程执行。
