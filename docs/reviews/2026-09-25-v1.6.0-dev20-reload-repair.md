## 调研、修复和结果

- dev.20 初次轮换后，旧 CLI 在 30s 预算中仅运行 8.806s 就报对象不稳定：目标原理图先成功回读，随后宿主恢复到 PCB，原实现继续用原理图探针失败三次便停止。原始失败未覆盖，见 `rotation/dev20-web-reload.json`。
- CLI 修复为使用剩余预算，save 后冻结组件 ID，重连后逐次检查工程/文档/tab 上下文、连续对象状态及末次 current；如宿主恢复同工程其他文档，最多一次 typed open 找回原目标。非空基线不能以空回包通过；合法空页需要至少四次、至少 700ms 连续空读，并明确只证明空页路由。
- 本轮 `--timeout 60s`：带 R8 的 P1 首次刷新 5.627s，ID/位号/坐标/引脚保持；唯一器件字段差异为 uniqueId 从空串变为 gge1，已保留 component-differences.json。没有证据确定赋值发生在前一次网表读取、保存还是刷新，因此不称完整器件字段不变。
- 以已有 gge1 的回读为基线，第二次刷新 5.091s，R8 完整器件记录完全一致。临时 R8 删除后又保存和 doc reload。
- 空 PCB 整页刷新 6.105s，返回 stable-empty-page-routing；前后完整 dump 除 capturedAt 外完全相同。
- 三次新 CLI 现场刷新均不需要 document.open、没有失败调用；“先成功再漂移、一次恢复期间仍旧页、随后恢复”的分支由离线状态迁移测试验证，未冒称本轮现场触发了它。
- 最终改动只涉及 CLI/Skill，dev.20 连接器 runtime JS 与 manifest 的 SHA256 和已导入包一致；包内只有 CHANGELOG 排版变化，无需再次导入。最终 CLI、源码、包 SHA 保存在本证据目录上一级的 `../final-runtime-sha256.json`。
